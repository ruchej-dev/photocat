# M21 — переименование файлов на диске

Запрос владельца (2026-11-23): «Добавить функцию переименования файла на диске, как одного, так
выбранных или всех по маске.»

**Это единственная задача проекта, которая меняет имя оригинала.** AGENTS.md §1 сегодня прямо
запрещает переименование, и запрет не «устарел» — он защищал архив от инструмента, который
однажды перепутает имена. Поэтому M21 — не «добавить кнопку», а **изменить конституцию узко и
обратимо**, и только после подтверждения владельцем формулировки (§1).

---

## 1. Что именно разрешается и что остаётся запрещённым

Новое исключение из §1 (предлагаемая формулировка, вносится в `AGENTS.md` тем же коммитом, что и
код):

> **Исключение, явно запрошенное владельцем:** `src/rename.rs` переименовывает оригинал в его же
> каталоге по явному действию человека — сначала план, затем подтверждение. Переименование не
> удаляет, не перемещает и не перезаписывает: занятое имя — отказ, другой каталог — отказ. Каждое
> переименование пишется в журнал `renames` и отменяется командой «Отменить». Никакого
> автоматического, пакетного без подтверждения или «умного» переименования при индексации нет.

Остаётся запрещённым без исключений:

- удаление и перемещение файлов архива (только системная корзина по подтверждению, `recycle.rs`);
- перезапись содержимого (никаких «поправить EXIF/имя внутри файла»);
- переименование при индексации, при выгрузке, при раскладке — только по кнопке/команде;
- переименование файлов вне `settings.roots`, симлинков и особых файлов;
- переименование, которое меняет каталог (`fs::rename` только внутри `parent()`), и «умные»
  шаблоны, подставляющие путь.

## 2. Границы модуля

- Новый `src/rename.rs` (L2, зависит от `db`), как `organize.rs`: план → применение, никакого
  egui, никаких SQL-строк в `app.rs`.
- `.pi/skills/enforce-architecture/scripts/check.sh` получает **второе** исключение в проверке №3:
  `fs::rename` разрешён только в `src/rename.rs` (сегодня — нигде). Исключение для `storage.rs`
  остаётся про кэш. Строка «архив не переименовывается» в выводе скрипта меняется на честную:
  «кэш — `storage.rs`, оригиналы — только `rename.rs` по подтверждению».
- `rename` регистрируется в карте слоёв (`ALLOWED`) и в `AGENTS.md` §3; `app`/`main` получают его в
  списке разрешённых.
- `SCHEMA_VERSION` 5 → 6 (`collections` из M19 уже там): только `CREATE TABLE IF NOT EXISTS`.

```sql
CREATE TABLE IF NOT EXISTS renames(
  id       INTEGER PRIMARY KEY,
  batch    TEXT NOT NULL,      -- ISO-время старта + случайный суффикс: один прогон = один batch
  file_id  INTEGER NOT NULL,
  old_path TEXT NOT NULL,
  new_path TEXT NOT NULL,
  at       TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS renames_batch ON renames(batch);
```

Журнал — не «история ради истории»: без него отмена невозможна, а без отмены переименование
оригиналов недопустимо.

## 3. План, подтверждение, применение

1. **План** (всегда, в CLI без `--apply` и в GUI до нажатия): таблица `старое → новое`, счётчики
   «переименовать N, пропустить M (уже так называется / имя занято / не UTF-8 / симлинк / вне
   корня / в корзине / файла нет)», первые 50 строк в CLI, весь список — в `<кэш>/photocat/`.
2. **Подтверждение**: в GUI — диалог с числами и явной кнопкой «Переименовать N файлов» (не
   «ОК»); в CLI — `--apply`. Без подтверждения план не применяется. Пакет больше 100 файлов
   дополнительно требует ввода числа файлов в поле подтверждения (защита от «нажал не то»).
3. **Применение** по файлу:
   1. исходник существует, обычный файл, не симлинк, внутри `settings.roots`, не в корзине,
      не в процессе индексации (индексация и переименование не идут одновременно: флаг занятости
      общий, как у проходов CLIP/OCR);
   2. целевое имя вычислено и санитизировано (`organize::component`/`tidy` — один санитайзер на
      проект), путь — тот же каталог; `rename` в другой каталог невозможен по построению;
   3. цель не существует; если «существует» — это тот же файл (сравнение `canonicalize`) и
      меняется только регистр — переименование разрешено; иначе пропуск с причиной;
   4. в БД нет строки с целевым путём (иначе — отказ: «в индексе уже есть путь X»);
   5. `fs::rename`; при ошибке — запись в отчёт, переход к следующему файлу;
   6. `UPDATE files SET path=? WHERE id=?`; если обновлено 0 строк — обратный `rename` и ошибка;
   7. `INSERT INTO renames(...)`. Пакет пишется в журнал по мере успеха, а не в конце: падение
      посередине оставляет честную запись того, что уже случилось.
4. **Отчёт**: переименовано, пропущено (с причинами), ошибок; в GUI — строка в статусе и
   «Скопировать отчёт».

## 4. Отмена

`photocat rename --undo BATCH` и кнопка «Отменить переименование» в GUI.

- Отменяется только пара, у которой `new_path` существует, а `old_path` — нет. Иначе строка
  пропускается с причиной: файл уже переименовали снова, имя заняли, файл удалён.
- Отмена — тоже переименование: та же проверка каталога, тот же санитайзер, тот же журнал (новая
  запись `batch` с пометкой `undo`).
- Отмена не «восстанавливает» ничего, кроме имени: содержимое, дата, sha256, теги, подборки и лица
  не менялись, потому что ключ всех таблиц — `file_id`, а не путь.

## 5. Маска и режимы

| Режим | Откуда | Что делает |
|---|---|---|
| Один файл | инспектор, «Переименовать…» | шаблон или новое имя для одного файла |
| Выбранные | выделение M18, N файлов | шаблон для каждого, счётчик `{n}` по порядку выделения |
| Все по маске | текущий фильтр/поиск, N файлов | шаблон + фильтр «имя содержит»/подстрока; область всегда показана числом и требует подтверждения |

Шаблон — тот же движок, что у витрины и выгрузки: `{date} {time} {camera} {tag} {orig} {ext}`
плюс `{n}` (номер с ведущими нулями) и `{hash8}`. Новых подстановок-путей нет: `{dir}`, `{root}`,
`{parent}` запрещены — иначе переименование станет перемещением.

Регулярка (`^IMG_(\d{8})_(\d{6})\.jpg$ → PXL_$1_$2.jpg`) — **новая зависимость** (`regex`, ~1.5 МиБ
кода). Без ADR её не добавляем: по умолчанию маска = шаблон + «имя содержит». Если владельцу нужны
регексы, это отдельный ADR 0037 и отдельная задача.

## 6. Что становится устаревшим и об этом надо сказать в интерфейсе

- **Слепок `sha256sum`** (M8) привязан к путям: после переименования `verify --manifest` покажет
  «нет в каталоге 1 / нет в слепке 1» на каждый переименованный файл. После массового
  переименования слепок надо переписать; приложение пишет об этом в диалоге и в `doctor`.
- **Витрина `organize --apply`**: hardlink на тот же inode продолжает работать, но имя в витрине
  остаётся старым. Пересобрать витрину — решение владельца, автоматически не трогаем.
- **Внешние бэкапы** (`rsync`, `restic`) увидят переименование как удаление + добавление;
  по содержимому потери нет, но следующий бэкап перенесёт файл заново. Это записано в §8 AGENTS.md
  и в `docs/ARCHITECTURE.md`.
- **Индексация** не считает файл новым: ключ пропуска — путь+размер+mtime, путь обновлён в БД,
  размер и mtime не менялись. Критерий приёмки, а не пожелание.

## 7. Критерии приёмки M21

1. `AGENTS.md` §1 содержит исключение (§1 выше), §3 — строку `rename.rs`, §8 — последствия для
   слепка и бэкапа; `docs/DECISIONS.md` — ADR 0035 «Переименование оригиналов: узкое исключение и
   журнал»; `check.sh` разрешает `fs::rename` только в `src/rename.rs` и краснеет, если он появился
   в любом другом файле (проверено на подсадной строке).
2. Без `--apply` и без подтверждения в GUI на диске не меняется ничего; план печатается и
   показывает причины пропуска.
3. Один файл, выбранные (M18) и «все по маске» (текущий фильтр) работают; `{n}` и `{hash8}` дают
   уникальные имена; область действия всегда видна числом.
4. Занятое имя — пропуск, не перезапись; смена только регистра разрешена; другой каталог, симлинк,
   не-UTF-8 имя, файл вне корня, файл в корзине — отказ с причиной; ошибка ФС не валит пакет.
5. `files.path` обновлён, повторная индексация после переименования не находит ни одного нового
   файла и не тратит время на хеширование; превью, теги, лица, подборки и решения по дублям
   на месте (ключ — `file_id`/`sha256`).
6. Журнал: пакет виден в `photocat rename --log`, отмена возвращает имена; отмена после чужого
   переименования в тот же путь — отказ, а не порча; отмена переживает перезапуск.
7. Тесты: план не трогает диск; один файл и пакет; коллизия; регистр; `{n}`; не-UTF-8; симлинк;
   вне корня; корзина; откат `UPDATE` при сбое; отмена и её отказы; миграция схемы 5→6 на копии
   реальной БД.
8. Замер на корпусе: переименование 100 выбранных файлов по шаблону (время, ошибок 0), повторная
   индексация — 0 обработанных, отмена — время и число возвращённых имён; числа в
   `docs/ARCHITECTURE.md` §Замеры.
9. GUI: пункт «Переименовать…» в инспекторе и в панели выделения; диалог плана; после применения —
   статус и возможность отмены. Короткий `timeout 6 gui` без падений.

## 8. Не делать

- Автоматическое переименование при индексации, при выгрузке, при раскладке, по расписанию.
- Перемещение между каталогами, «разложить по датам» через переименование (для этого есть
  `organize` — он создаёт ссылки и не трогает оригиналы).
- Перезапись существующих файлов, «умное» слияние имён, транслитерацию по вкусу.
- Сеть, отправку имён и путей куда-либо.
- Регулярные выражения без ADR и отдельного решения владельца.

## 9. Открытые вопросы к владельцу

1. **Формулировка исключения** в §1 (текст в §1 выше) — согласна ли? Пока не подтверждена, задача
   остаётся в очереди и код не пишется.
2. **Регулярка или шаблон?** Предлагаю шаблон `{date}_{time}_{orig}` + «имя содержит»: без новой
   зависимости. Регексы — отдельный ADR.
3. **Подтверждение пакета:** порог «ввод числа файлов» — 100 или другое число?
4. **Что делать с витриной и слепком после массового переименования:** только предупредить (предлагаю)
   или сразу предложить «Пересобрать витрину»/«Переписать слепок» кнопкой?
