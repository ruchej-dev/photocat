# I18N — language of the interface and of the repository

Status: **in progress** (M21). Owner: the interface language is chosen in "Settings → Interface";
the repository language is English, with the Russian documentation kept as the second variant.

## What exists

- `src/i18n.rs` (L0): `Lang` (`En` default, `Ru`), `Lang::parse`/`code`/`label`, `english(ru)` and
  `t(lang, ru)`. The table `PAIRS` maps a Russian source string to its English text. A string that is
  missing from the table is shown in Russian — it never disappears and never renders as a key.
- `settings.lang` (`en`/`ru`) in the DB; saved the moment it is chosen. On the very first
  launch (no `lang` row yet) the language comes from the system locale — a set `LC_ALL` or
  `LC_MESSAGES` decides on its own (`C`/`POSIX`/unknown → English), otherwise `LANGUAGE` (a
  preference list) and `LANG` — and is written to the DB once (`db::ensure_lang`, called by
  `app::run` and `photocat settings`).
  No release exists yet, so an old DB without the row is simply re-detected.
- "Settings → Interface" — the only place the language is chosen; the dialog is the first tab so the
  control is one click away.
- `photocat settings --lang en|ru` for the CLI; `photocat settings` prints the current language.

## Rules for a translated screen

1. The source string stays Russian and goes through `t(lang, "…")`; dynamic fragments are translated
   as parts (`format!("{}: {e}", t(lang, "…"))`).
2. Add the pair to `PAIRS` in the same commit; the table test rejects duplicates but cannot see a
   forgotten call site.
3. A screen is "translated" only when **every** label on it goes through `t()`; a half-translated
   screen is worse than a Russian one, so the screen is done in a single commit.
4. Content, not labels: month names, `db::human()` units (`КиБ/МиБ/ГиБ`) and file dates stay as they
   are until the content panes move; when they move, they move together with the panes.
5. The chosen language is read from `Settings` (`self.settings.lang`) and passed down; there is no
   global language variable, so tests stay independent.

## Acceptance for a screen

1. `cargo test` — a headless frame of the screen contains the English label and no Russian one for
   the strings covered by this commit.
2. `cargo clippy --all-targets` and `bash .pi/skills/enforce-architecture/scripts/check.sh` clean.
3. `plan/STATUS.md` entry with the screen, the number of strings and the test that proves it.
4. `plan/I18N.md` table row moved from `todo` to `done`.

## First launch and the CLI

`db::ensure_lang` runs before the window opens and before `photocat settings` prints anything: if the
`lang` key is absent, the system locale decides and the result is stored, so the choice is
made once and remembered until the owner changes it. CLI reports (M21.6) will take the language from
`settings.lang` explicitly — the same rule as the GUI: no process-wide mutable language.

## Not doing

- A translation framework (gettext, fluent, `rust-i18n`): a new dependency for two languages, see
  ADR 0040.
- Machine translation of documentation: a document is translated by hand, in the same style, with the
  numbers kept.
- Translating identifiers, DB enums (`grid_layout = months|flat`) or settings keys: they are data,
  not labels.
