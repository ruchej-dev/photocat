# I18N — language of the interface and of the repository

Status: **reversed in M23** (ADR 0046). Owner: the interface language is chosen in
"Settings → Interface"; the repository language is English, with the Russian documentation kept as
the second variant. Since M23.1 the source text in the code is English and Russian is the
translation (ADR 0040 had it the other way round).

## The direction (M23)

- `src/i18n.rs` (L0): `Lang` (`En` default, `Ru`), `Lang::parse`/`code`/`label`, `russian(en)` and
  `t(lang, en)`. The table `PAIRS` maps an English source string to its Russian text. A string that
  is missing from the table is shown as written — in English, the source, which never disappears
  and never renders as a key.
- `i18n::count(lang, n, noun)` takes a noun key (`file`, `photo`, `shot`, `person`, `group`, `tag`,
  `album`, `sub_album`); both plural sets live in `i18n.rs`, so no screen holds a Russian word.
- `i18n::USAGE` is `(English, Russian)`; `.0` is the English key the CLI prints through `t()`.
- Identifiers, comments, doc comments, logs and error text are English. Cyrillic remains only in the
  Russian column of `PAIRS`, in the `*.ru.md` documents and in the model prompts (`embed.rs`).
- `tests/source_language.rs` is the guard, in three checks: a Cyrillic identifier fails anywhere; a
  Russian comment or production string fails in a module that is already converted; a Russian
  *message* fails inside `#[cfg(test)]` too — an assertion message, `panic!`/`bail!`/`anyhow!` text,
  `expect("…")` or an `#[ignore = "…"]` reason (M23.5). What a test compares is data and stays
  Russian where the window must show Russian: `assert_eq!(t(Lang::Ru, "Settings"), "Настройки")`.
  The `PENDING` list names the modules that still hold Russian and only shrinks (empty since M23.4).
- `settings.lang` (`en`/`ru`) in the DB; saved the moment it is chosen. On the very first

## Rules for a translated screen

1. The source string is English and goes through `t(lang, "…")`; dynamic fragments are translated
   as parts (`format!("{}: {e}", t(lang, "…"))`).
2. Add the pair to `PAIRS` in the same commit; the table test rejects duplicates but cannot see a
   forgotten call site.
3. A screen is "translated" only when **every** label on it goes through `t()`; a half-translated
   screen is worse than a Russian one, so the screen is done in a single commit.
4. Content, not labels: month names (`i18n::month_name`), the units (`db::human_in` — `КиБ/МиБ` or
   `KiB/MiB`) and the date format follow the language since M21.2; file names, paths, tag labels and
   OCR text stay data in whichever language the owner wrote them.
5. The chosen language is read from `Settings` (`self.settings.lang`) and passed down; there is no
   global language variable, so tests stay independent.

## Acceptance for a screen

1. `cargo test` — a headless frame of the screen contains the English label and no Russian one for
   the strings covered by this commit.
2. `cargo clippy --all-targets` and `bash .pi/skills/enforce-architecture/scripts/check.sh` clean.
3. `plan/STATUS.md` entry with the screen, the number of strings and the test that proves it.
4. `plan/I18N.md` table row moved from `todo` to `done`.

## First launch and the CLI

`db::ensure_lang` runs before the window opens and before `photocat settings` prints anything: if the
`lang` key is absent, the system locale decides and the result is stored, so the choice is
made once and remembered until the owner changes it. Since M21.6 every CLI command reads
`settings.lang` the same way (`main::language(&args)` opens the cache DB once and calls
`db::ensure_lang`), then passes it into the report — no process-wide mutable language. A command that
prints a report therefore needs the cache DB; `verify` and `manifest` only read the archive, the DB
is not their input.

## M23 additions

M23 moved the source of every string to English (ADR 0046). Two rules the conversion made explicit:

- A comparison the code makes against a *label* must go through the dictionary, never through a
  hard-coded word: after the default labels became English, `ocr::wants_text` had to ask the
  dictionaries which labels the `document`/`screenshot` ids carry. It does that in `db`
  (`text_tag_labels`), so the OCR module still knows neither the model nor its catalogue (M23.6).
- A test message is English, a test *datum* is not: `assert_eq!(t(Lang::Ru, "Settings"),
  "Настройки")` keeps the Russian expectation, `assert!(plan.candidates == 1, "…")` carries an
  English sentence. The template a test exercises (`labels()` in `ocr` — `document`/`screenshot`)
  follows the default dictionary, which is English since M23.3.

## Not doing

- A translation framework (gettext, fluent, `rust-i18n`): a new dependency for two languages, see
  ADR 0040.
- Machine translation of documentation: a document is translated by hand, in the same style, with the
  numbers kept.
- Translating identifiers, DB enums (`grid_layout = months|flat`) or settings keys: they are data,
  not labels.
