# M19–M20 — альбомы в БД и выгрузка физическим каталогом

Запрос владельца (2026-11-23): «Добавь возможность создавать каталоги. Эти каталоги только данные
в базе, не на диске. Правило: все операции только с данными, не с файлами по факту, кроме спец
инструментов. Добавить функцию выгрузки каталогов: сформированный каталог выгружается на диск
с файлами. Но надо решить проблему совпадения имён.»

Уточнения владельца (2026-11-23):

- слово — **«Альбомы»**, не «каталоги»;
- **вложенность обязательна**: альбом может содержать подальбомы;
- **задача альбома — создать физический каталог с упорядоченными данными**: структура и порядок,
  собранные в приложении, повторяются на диске один в один;
- **выгрузка — файлами, не ссылками**, каталоги подальбомов **без номеров** (порядок подальбомов
  на диске алфавитный — так и решено), имена файлов — `{n}_{orig}`;
- **один снимок — одна строка в альбоме**: дважды в один альбом файл не попадает (это ключ БД, а
  не проверка в интерфейсе); в разных альбомах — можно;
- переименование файлов на диске **убрано** из просьбы: оригиналы неприкосновенны (AGENTS.md §1,
  ADR 0005).

Отсюда два шага: **M19** — альбомы как данные (дерево + порядок, ни одного файла на диске),
**M20** — выгрузка дерева на диск настоящими файлами по явному `--apply`.

---

## 1. Слово

- «Каталоги (N)» в интерфейсе уже заняты папками архива (`settings.roots`), поэтому альбомы —
  отдельное слово. **В интерфейсе:** «Альбомы», «Альбом «Дача 2024»», «В альбом». **В коде:**
  `album`, `albums`, `album_files`. **В CLI:** `photocat albums …`, `photocat export --album N`.
- Старое «альбом = день календаря» (M13) отменено: день остаётся днём, альбом — явный набор
  файлов с порядком и вложенностью.

## 2. Что такое альбом

Дерево узлов, которое владелец собирает руками, чтобы получить на диске готовый каталог:
«Дача 2024» → «Май», «Июнь»; «Лиза» → «1 год», «2 года»; «На печать». Узел содержит **файлы в
заданном порядке** и **подальбомы в заданном порядке**.

- Альбом ничего не знает о файле кроме `files.id`; файл может быть в нескольких альбомах и в
  нескольких местах одного дерева (это осознанно: один снимок уместен и в «Дача 2024», и в
  «На печать»).
- Альбом живёт в БД; удаление — только строки. Файл на диске цел.
- Файл в корзине приложения (`files.trashed_at`) остаётся строкой альбома, но в сетке скрыт,
  счётчик пишет «в корзине N».
- Файл пропал из индекса (сброс индекса, каталог убран) — строки альбома на него удаляются тем же
  действием `db`; «висячих» ссылок не бывает.
- Порядок — часть данных, а не представления: сортировка сетки (M17) его не меняет, а внутри
  альбома по умолчанию показывается «порядок альбома».

## 3. Схема БД (M19)

`SCHEMA_VERSION` 4 → 5, только `CREATE TABLE IF NOT EXISTS` (ADR 0002/0003): данные не теряются,
старая БД открывается, повторное открытие не пишет, пока версия совпадает.

```sql
CREATE TABLE IF NOT EXISTS albums(
  id         INTEGER PRIMARY KEY,
  parent_id  INTEGER NOT NULL DEFAULT 0,  -- 0 — корень дерева (не NULL: NULL в UNIQUE не сравнивается)
  position   INTEGER NOT NULL DEFAULT 0,  -- порядок среди соседей
  name       TEXT NOT NULL,               -- как назвал владелец, ≤ 80 символов
  name_key   TEXT NOT NULL,               -- name.to_lowercase(): уникальность без учёта регистра
  note       TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS albums_sibling_name ON albums(parent_id, name_key);
CREATE INDEX IF NOT EXISTS albums_tree ON albums(parent_id, position);

CREATE TABLE IF NOT EXISTS album_files(
  album_id INTEGER NOT NULL,
  file_id  INTEGER NOT NULL,
  position INTEGER NOT NULL DEFAULT 0,   -- порядок внутри альбома
  added_at TEXT NOT NULL,
  PRIMARY KEY(album_id, file_id)
);
CREATE INDEX IF NOT EXISTS album_files_file ON album_files(file_id);
```

- `parent_id = 0` — корень. `PRAGMA foreign_keys` в `db::open` не включён, поэтому `ON DELETE
  CASCADE` не сработает: удаление поддерева и очистка `album_files` делаются явно, в одной
  транзакции (`delete_album` рекурсивно; удаление строк `files` при сбросе индекса и «убрать
  каталог» чистит `album_files`). Тесты на все пути обязательны.
- Имя уникально **среди соседей** без учёта регистра (`parent_id`, `name_key`), а не глобально:
  «2023/Дача» и «2024/Дача» — разные альбомы.
- `position` — плотный 0..n−1 у соседей; `db` перенумеровывает после вставки/перемещения/удаления,
  чтобы порядок не «разъезжался» дырками.
- Обложка не хранится: первый неудалённый файл по `position`, иначе по дате. Иначе — пустая
  папка-иконка.
- Глубина не ограничена искусственно, но цикл запрещён: `move_album` отказывает, если новый
  родитель — сам альбом или его потомок (проверка обходом вверх).

## 4. API и CLI

`src/db.rs` (L1), без логики интерфейса:

| Функция | Что делает |
|---|---|
| `create_album(conn, parent_id, name, note) -> i64` | имя, `name_key`, `position` в конец |
| `rename_album(conn, id, name)` | проверка соседей + `updated_at` |
| `move_album(conn, id, new_parent, position)` | отказ на цикл, перенумерация соседей |
| `delete_album(conn, id)` | поддерево: `album_files` → `albums`, только строки |
| `add_to_album(conn, id, &[file_id]) -> (добавлено, уже было)` | в конец, идемпотентно |
| `remove_from_album(conn, id, &[file_id])` | перенумерация |
| `move_in_album(conn, id, file_id, delta)` | «выше/ниже» в порядке альбома |
| `albums_tree(conn) -> Vec<AlbumNode>` | id, parent, position, имя, note, файлов, объём, обложка, глубина |
| `album_items(conn, id) -> Vec<FileRow>` | по `position` |
| `albums_of_file(conn, file_id) -> Vec<String>` | для инспектора |

CLI (`src/main.rs`), headless — им и проверяем:

```
photocat albums list [--tree]
photocat albums new --name "Дача 2024" [--parent ID] [--note "..."]
photocat albums rename --id N --name "..."
photocat albums move --id N --parent ID [--position K]
photocat albums add --id N PATH...          # пути ищутся в индексе, не на диске
photocat albums remove --id N PATH...
photocat albums delete --id N [--yes]       # поддерево, только строки
photocat albums show --id N [--tree]
```

Ни одна команда не открывает файл по пути и не пишет на диск: `PATH` — ключ в `files.path`, а не
файловая операция.

## 5. Интерфейс (M19)

- Левая панель, группа «БИБЛИОТЕКА»: пункт **«Альбомы (N)»** с числом альбомов.
- Вид «Альбомы»: дерево с отступами и треугольниками свёртывания; у узла — обложка, имя,
  «N файлов · M подальбомов · объём». Сверху «+ Новый альбом»; у выбранного — «+ Подальбом»,
  «Переименовать», «Переместить в…» (выбор родителя из дерева; свои потомки в списке недоступны),
  «Выше / Ниже» (порядок среди соседей), «Удалить альбом».
- Внутри альбома: строка подальбомов (плитки-папки, тот же порядок), ниже — сетка файлов
  (`draw_cell`), чип «Альбом «Имя»» с «×». Действия: **«Добавить выбранные»** (M18),
  **«Убрать из альбома»**, **«Выше / Ниже»** для файла (порядок), **«Выгрузить на диск…»** (M20).
- Сортировка внутри альбома по умолчанию — «Порядок альбома» (новый вариант в списке M17, доступен
  только внутри альбома); «По дате» и «По имени» остаются как временный взгляд.
- Удаление: подтверждение показывает поддерево («удалить «Дача 2024», «Май», «Июнь» — 3 альбома,
  412 строк; файлы на диске останутся»).
- Пусто: «В альбоме пока нет файлов — выберите снимки в сетке и нажмите «Добавить выбранные»».
- Инспектор: строка «альбомы — Дача 2024 / Май, На печать» с «×».

## 6. M20 — выгрузка альбома физическим каталогом

**Выгрузка — это копия файлов**, а не ссылки: цель альбома — готовый каталог, который можно
отдать, залить или открыть без архива. `--mode` у `export` нет; ссылки остаются у `organize`
(витрина), это разные инструменты с разными задачами.

```
photocat export --album N --out DIR [--name TEMPLATE] [--apply]
```

- `--out DIR` — каталог, **внутри** которого создаётся корневой каталог альбома N; сам `--out`
  должен существовать и не быть каталогом архива.
- Структура повторяет дерево альбомов: `--out/<альбом>/<подальбом>/…`, в каждом каталоге —
  свои файлы. Порядок файлов виден в файловом менеджере, потому что имя начинается с номера
  позиции (`{n}`), а не с даты.
- `--name` по умолчанию `{n}_{orig}`; поддерживаются `{date} {time} {camera} {tag} {orig} {ext}`
  и `{n}`, `{hash8}`. `{n}` — позиция файла в его альбоме, ширина — по числу файлов (2 знака до
  99, 3 дальше), так что «01_», «02_», … без путаницы.
- **Каталоги подальбомов без номеров** (решено владельцем): на диске они идут по алфавиту, потому
  что файловая система не знает `position`. Порядок подальбомов остаётся порядком дерева в
  приложении, а упорядоченность «данных» обеспечивают номера в именах файлов.
- Пустой альбом — пустой каталог: структура важнее, чем «не создавать пустое».
- Код в `src/organize.rs` (L2): `plan_album(...)` + `apply_copy(plan)`. Новый модуль не заводим,
  чтобы не появилась зависимость L2→L2; `organize` уже умеет копировать и чистить имена.
  Существующий `apply` (hard/copy/symlink для витрины) не меняется.

### 6.1. Совпадение имён — разбор и правило

Вложенность и номер позиции убирают большинство коллизий **по построению**; остаются пять случаев.

| Вид | Пример | Правило |
|---|---|---|
| Одинаковые имена файлов в одном альбоме | `IMG_0001.jpg` дважды | префикс позиции делает имена разными: `01_IMG_0001.jpg`, `02_IMG_0001.jpg` |
| Имя уже занято в цели другим содержимым (правка руками, прошлая выгрузка) | `01_IMG_0001.jpg` есть, но с другим `sha256` | не перезаписывать: `01_IMG_0001-2.jpg`; в плане видно, что именно переименовано |
| Имя уже занято тем же содержимым | повторная выгрузка того же альбома | **пропустить** («уже выгружен»), а не создавать `-2`: прогон идемпотентен |
| Имена подальбомов после чистки ФС совпали | «Дача/2024» и «Дача:2024» → `Дача_2024` | второму каталогу `-2`, в плане сказано, почему |
| Регистр/нормализация | `A.JPG` и `a.jpg` на Windows/macOS | сравнение без учёта регистра на Windows/macOS (`cfg`); NFD/NFC на macOS — известное ограничение, лечится `{hash8}` |

Чистка имён до сравнения: недопустимые для ФС символы (`: ? * " < > |` и `/` в имени альбома),
имена устройств Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9`), точка/пробел в конце,
длина компонента ≤ 120 символов, полный путь ≤ 240 (запас до 260 в Windows), пустое имя →
`{hash8}`. Санитайзер один — `organize::component`/`tidy`; второй копии нет.

Повтора одного снимка в каталоге не бывает по построению: в альбоме снимок — одна строка
(`PRIMARY KEY(album_id, file_id)`), а один и тот же снимок в двух разных альбомах даёт два разных
каталога. Это решено владельцем: «один».

Проверка «то же содержимое» — по `sha256` из БД для исходника и по факту для цели (чтение целей
идёт в фоне, прогресс виден, кнопка «Стоп»; это чтение, не запись). Кэш «что уже выгружали»
(`<кэш>/photocat/exports/<album>-<время>.txt`) ускоряет повтор, но не отменяет проверку.

**Честное ограничение порядка.** Файлы не переименовываются в цели (AGENTS.md §1), поэтому после
переупорядочивания альбома повторная выгрузка не переносит уже выгруженный файл на новую позицию —
он остаётся под старым номером, а новый пропускается как «уже выгружен». Правильный путь — удалить
старый каталог выгрузки руками и выгрузить заново; приложение об этом пишет в плане и в отчёте
(«порядок в цели устарел: N файлов»). Удалять и переименовывать в `--out` приложение не будет.

### 6.2. План и отчёт

План — дерево: каталоги, в каждом — файлы «старое имя → новое имя»; счётчики «скопировать N
файлов · X ГиБ», «пропущено N (уже выгружено)», «переименовано из-за коллизии N», «нет файла на
диске N», «пути длиннее 240 символов N». Без `--apply` не создаётся ничего, даже каталог `--out`.

Отчёт после `--apply`: создано файлов, пропущено, ошибок, байт записи; в GUI — строка в статусе и
«Скопировать отчёт». Копия отчёта — в кэше, не в архиве.

### 6.3. Критерии приёмки M20

1. Без `--apply` — только план, на диске ничего; `--out` не существует, `--apply` без `--out`,
   `--out` внутри любого `settings.roots` — отказ с кодом 2 и объяснением.
2. Структура на диске повторяет дерево: `--out/<альбом>/<подальбом>/…`, файлы только в своих
   каталогах, пустой альбом даёт пустой каталог; каталоги подальбомов без номеров — на диске они
   идут по алфавиту, порядок дерева остаётся в приложении.
3. Файлы — настоящие копии (inode и размер отличаются от оригинала, содержимое то же по `sha256`),
   никаких ссылок; оригинал не открыт на запись.
4. Порядок: имена начинаются с `{n}` по `position`; до 99 файлов — два знака; «Дача/Май» и
   «Дача/Июнь» сортируются в файловом менеджере в том же порядке, что и альбом.
5. Коллизии — по таблице §6.1 (пять строк), включая совпадение имён подальбомов после чистки и
   идемпотентность по `sha256`; ничего не перезаписывается и не удаляется. Один снимок дважды в
   одном каталоге невозможен: в альбоме он одна строка.
6. Отчёт: скопировано / пропущено / ошибок / байт записи / «порядок в цели устарел N»; ошибка
   одного файла (нет на диске, нет прав) не валит проход.
7. GUI: «Выгрузить на диск…» — поле каталога, шаблон имени, галочка номеров подальбомов; сначала
   план-дерево, затем «Выгрузить N файлов»; прогресс и «Стоп» в верхней панели.
8. Тесты: чистка имён и редко используемые символы, пять видов коллизий, идемпотентность, копия
   (не ссылка), пустой альбом, глубина 3, отказ `--out` в корне, отмена в середине (созданные
   файлы перечислены), отсутствующий исходник.
9. Замер на корпусе: дерево из 3 уровней, 500 файлов — время и объём копии; повтор — время и 0
   новых файлов; 2230 файлов — время и объём; `docs/ARCHITECTURE.md` §Замеры.
10. ADR 0035 «Выгрузка альбома: структура альбома, копии файлов, ничего не перезаписывается»,
    `docs/UI.md`, `plan/M19-albums.md`, `plan/STATUS.md`.

### 6.4. Не делать в M20

- Не выгружать ссылками, не добавлять `--mode`: для ссылок есть `organize` (витрина).
- Не удалять и не переименовывать в `--out`, не «синхронизировать» цель.
- Не писать в `--out` служебные файлы (манифест, `.photocat/`, JSON) — каталог остаётся чистым.
- Не выгружать автоматически по расписанию, при старте или при изменении альбома.
- Не индексировать `--out` молча.

## 7. Порядок работ

1. M18 (мультивыбор) — иначе «Добавить выбранные» нечего нажимать.
2. M19: схема (дерево, `position`) → `db` → CLI `--tree` → тесты миграции на копии реальной БД →
   вид «Альбомы» с вложенностью и порядком → «Порядок альбома» в сортировке M17 → `docs`.
3. M20: `plan_album` (дерево, коллизии, `{n}`) → CLI `--apply` → GUI-план-дерево → замеры →
   ADR 0035.

карточка файла), `storage.rs` (сброс индекса чистит `album_files`), ADR 0034.
Ни одной файловой операции: `fs::remove_*`/`fs::rename` в `src/` по-прежнему нет.

- **Данные.** `parent_id=0` — корень, имя уникально среди соседей (`parent_id, name_key`),
  `position` плотный 0..n−1, `PRIMARY KEY(album_id,file_id)` — один снимок один раз в альбоме.
  `delete_album` рекурсивно чистит поддерево; удаление строк `files` чистит `album_files` и
  сжимает порядок. Цикл запрещён в `move_album`.
- **CLI.** `list [--tree] | new | rename | move | add | remove | delete [--yes] | show [--tree]`;
  пути — ключ `files.path`, файлы не открываются. Коды: 0 — сделано, 1 — ошибка данных,
  2 — аргументы/отказ без `--yes`.
- **GUI.** Дерево в панели содержимого, «+ Новый альбом / + Подальбом / Переименовать /
  Переместить в… / Выше / Ниже / Удалить альбом», плитки подальбомов и сетка в порядке альбома.
  «В альбоме / Все файлы» — временный взгляд для «Добавить выбранные» (M18): смена вида по-прежнему
  снимает выделение, поэтому набирать снимки нужно внутри вида. «Выгрузить на диск…» погашена до M20.
- **Порядок.** `GridSort::Album` доступен только внутри альбома; вне его — дата ↓. Одна функция
  `App::ordered` отдаёт порядок сетке, полному экрану и выделению; смена альбома снимает выбор
  с причиной.
