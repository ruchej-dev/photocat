# M19–M20 — альбомы в БД и выгрузка на диск

Запрос владельца (2026-11-23): «Добавь возможность создавать каталоги. Эти каталоги только данные
в базе, не на диске. Правило: все операции только с данными, не с файлами по факту, кроме спец
инструментов. Добавить функцию выгрузки каталогов: сформированный каталог выгружается на диск
с файлами. Но надо решить проблему совпадения имён.»

Решение владельца по слову: **не «каталоги», а «альбомы»**. Переименование файлов на диске из
той же просьбы владелец **убрал** — M21 отменён, оригиналы остаются неприкосновенными (AGENTS.md
§1, ADR 0005).

Здесь два шага: **M19** — альбомы как данные (ни одного файла на диске), **M20** — выгрузка
альбома на диск (единственное место, где шаг создаёт файлы, и только по явному `--apply`).

---

## 1. Слово: «Альбомы», а не «Каталоги»

- «Каталоги (N)» в интерфейсе уже занимают папки на диске (`settings.roots`), поэтому альбомом
  их называть нельзя: владелец искал бы в одном слове два разных понятия.
- «Альбом = день календаря» — старое временное соглашение (`plan/BACKLOG.md` § M13): оно
  отменяется. День остаётся днём, **альбом — явный набор файлов**, который собирает владелец.
- **В интерфейсе:** «Альбомы» (список), «Альбом «Дача 2024»» (один), «В альбом» (действие).
- **В коде и БД:** `album`, `albums`, `album_files`.
- **В CLI:** `photocat albums …`, `photocat export --album N …`.
- **«Каталог»** остаётся только про папку на диске (`roots`, «Каталоги (N)», выбор папки).

## 2. Что такое альбом

Набор ссылок на файлы индекса, который владелец собрал руками: «Дача 2024», «Лиза 1 год»,
«На печать», «Отправить бабушке». Альбом ничего не знает о файле кроме `files.id`.

- Файл может быть в нескольких альбомах.
- Альбом живёт в БД и удаляется только строками: файл на диске цел.
- Файл ушёл в корзину приложения (`files.trashed_at`) — в альбоме он остаётся строкой, но в сетке
  скрыт, счётчик пишет «в корзине N».
- Файл пропал из индекса (сброс индекса, каталог убран) — строки альбома на него удаляются тем же
  действием `db`; «висячих» ссылок не бывает.
- Альбом не является фильтром: внутри альбома фильтр по типу/дате/тегу применяется как обычный
  (M17/M16), с чипом «Альбом «Дача 2024»».

## 3. Схема БД (M19)

`SCHEMA_VERSION` 4 → 5, только `CREATE TABLE IF NOT EXISTS` (ADR 0002/0003): данные не теряются,
старая БД открывается, повторное открытие не пишет, пока версия совпадает.

```sql
CREATE TABLE IF NOT EXISTS albums(
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,           -- непустое, обрезано по краям, длина ≤ 80
  note       TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,           -- ISO-8601 UTC, как files.taken_at
  updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS albums_name ON albums(name);

CREATE TABLE IF NOT EXISTS album_files(
  album_id INTEGER NOT NULL,
  file_id  INTEGER NOT NULL,
  position INTEGER NOT NULL DEFAULT 0,
  added_at TEXT NOT NULL,
  PRIMARY KEY(album_id, file_id)
);
CREATE INDEX IF NOT EXISTS album_files_file ON album_files(file_id);
```

- Имя альбома уникально без учёта регистра: уникальный индекс по `name` + проверка через
  `to_lowercase()` в `db::create_album` (SQLite `NOCASE` кириллицу не понижает, индекс остаётся
  страховкой от гонки).
- `PRAGMA foreign_keys` сегодня не включён (в `db::open` его нет), поэтому `ON DELETE CASCADE` не
  сработает. Удаление делается явно, двумя `DELETE` в одной транзакции: `delete_album` и любое
  удаление строк `files` (сброс индекса, `remove_root`) чистят `album_files`. Тесты на оба пути
  обязательны.
- Порядок внутри альбома — `position` (по умолчанию «как добавляли»), сортировка сетки (M17) его
  не меняет: это порядок данных, а не представления.
- Обложка не хранится: берётся первый неудалённый файл по `position`, иначе по дате. Выбор обложки
  руками — отдельное поле, если владелец попросит.

## 4. API и CLI

`src/db.rs` (L1), без логики интерфейса:

| Функция | Что делает |
|---|---|
| `create_album(conn, name, note) -> i64` | проверка имени, уникальность |
| `rename_album(conn, id, name)` | то же + `updated_at` |
| `delete_album(conn, id)` | `album_files` → `albums`, только строки |
| `add_to_album(conn, id, &[file_id]) -> (добавлено, уже было)` | идемпотентно |
| `remove_from_album(conn, id, &[file_id])` | |
| `albums_list(conn) -> Vec<AlbumRow>` | id, имя, note, число файлов, объём, обложка |
| `album_items(conn, id) -> Vec<FileRow>` | для сетки, по `position` |
| `albums_of_file(conn, file_id) -> Vec<String>` | для инспектора |

CLI (`src/main.rs`), headless — им и проверяем:

```
photocat albums list
photocat albums new --name "Дача 2024" [--note "..."]
photocat albums rename --id N --name "..."
photocat albums add --id N PATH...          # пути ищутся в индексе, не на диске
photocat albums remove --id N PATH...
photocat albums delete --id N [--yes]       # только строки
photocat albums show --id N
```

Ни одна команда не открывает файл по пути и не пишет на диск: `PATH` — это ключ в `files.path`,
а не файловая операция.

## 5. Интерфейс (M19)

- Левая панель, группа «БИБЛИОТЕКА»: пункт **«Альбомы (N)»** с числом альбомов.
- Вид «Альбомы»: список карточек — обложка, имя, «N файлов · объём», дата создания. Сверху
  строка «+ Новый альбом» (имя — текстовое поле в панели, без диалога).
- Внутри альбома: та же сетка (`draw_cell`, без второго рендерера), чип «Альбом «Имя»» с «×»,
  факты «N файлов · объём · в корзине K», действия: **«Добавить выбранные»** (нужен M18),
  **«Убрать из альбома»**, «Переименовать», «Удалить альбом» (подтверждение: «строки в базе;
  файлы на диске останутся»), **«Выгрузить на диск…»** (M20).
- Пусто: «В альбоме пока нет файлов — выберите снимки в сетке и нажмите «Добавить выбранные»».
- Инспектор: строка «альбомы — Дача 2024, На печать» с «×» у каждого.
- Никаких новых диалогов, кроме подтверждений и M20: правила `ui-design` (слово вместо иконки,
  одно действие — одна кнопка).

## 6. M20 — выгрузка альбома на диск

Единственный шаг, который создаёт файлы, и только так же, как `organize`: **сначала план, потом
`--apply`**. Оригиналы не трогаются, ничего не перезаписывается и не удаляется.

```
photocat export --album N --out DIR [--mode hard|copy|symlink] [--layout flat|day|month]
                [--name TEMPLATE] [--apply]
```

- `--mode hard` по умолчанию (0 байт), `copy` — реальная копия, `symlink` — ссылка. Как в
  `organize`: междоменная ФС для `hard` — ошибка по файлу, а не тихий переход в копию.
- `--layout flat` — всё в один каталог (по умолчанию), `day`/`month` — подкаталоги по дате через
  существующий `organize::Layout`.
- `--name` — тот же шаблон, что у витрины (`{date} {time} {camera} {tag} {orig} {ext}`), плюс
  `{n}` (порядковый номер с ведущими нулями, ширина по числу файлов) и `{hash8}` (8 hex от
  sha256). Шаблон по умолчанию для выгрузки — `{date}_{time}_{orig}`: одинаковых `IMG_0001.jpg`
  становится меньше ещё до разрешения коллизий.
- Код в `src/organize.rs` (L2): `plan_album(...)` + `apply(plan, mode)`. Новый модуль не заводим,
  чтобы не появилась зависимость L2→L2; слои `organize` уже разрешают `db`.

### 6.1. Совпадение имён — разбор и правило

Коллизии бывают четырёх видов, и лечатся они по-разному.

| Вид | Пример | Правило |
|---|---|---|
| Одно имя у разных снимков | `DCIM/100/IMG_0001.jpg` и `DCIM/101/IMG_0001.jpg` | шаблон по умолчанию `{date}_{time}_{orig}`; остаток — `-2`, `-3` (как в `organize`) |
| Имя уже занято в `--out` другим содержимым | второй прогон в тот же каталог | не перезаписывать: `-2`, `-3`; в плане видно «IMG_0001-2.jpg» |
| Имя занято тем же содержимым | повторная выгрузка того же альбома | **пропустить** («уже выгружен»), а не создавать `-2`: прогон идемпотентен |
| Разный регистр/нормализация | `A.JPG` и `a.jpg` на Windows/macOS | сравнение без учёта регистра на Windows/macOS (`cfg`), на Linux — как есть; NFD/NFC на macOS — известное ограничение, лечится `{hash8}` |

Дополнительно, до сравнения: недопустимые для ФС символы (`: ? * " < > |`), имена устройств
Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9`), точка/пробел в конце, длина ≤ 120
символов, пустое имя → `{hash8}`. Санитайзер один — `organize::component`/`tidy`; второй копии
нет.

Проверка «то же содержимое» — по `sha256` из БД для исходника и по факту для цели в `--out`
(хеширование целей идёт в фоне, прогресс виден, кнопка «Стоп»; это чтение, не запись).
Ограничение честное: на 5 тыс. целей повторный прогон читает их заново — кэш «что мы уже
выгружали» (`<кэш>/photocat/exports/<album>-<время>.txt`) ускоряет, но не отменяет проверку.

### 6.2. План и отчёт

План — таблица: сколько файлов, байт, каталогов, сколько имён изменено и почему, сколько
пропущено как «уже выгружено», сколько файлов нет на диске (файл исчез после индексации — строка
в альбоме остаётся, в план не попадает, счётчик «нет файла N»). Без `--apply` не создаётся
ничего, даже каталог `--out`.

Отчёт после `--apply`: создано ссылок/копий, пропущено, ошибок, байт записи; в GUI — строка в
статусе и «Скопировать отчёт». Копия отчёта — в кэше, не в архиве.

### 6.3. Критерии приёмки M20

1. `--apply` без `--out` и на несуществующий `--out` — отказ с кодом 2; `--out`, совпадающий с
   каталогом архива (любой `settings.roots`), — отказ с объяснением: выгрузка в архив запрещена.
2. Повторный прогон того же альбома в тот же `--out` — 0 новых файлов, 0 перезаписей, в отчёте
   «пропущено N: уже выгружено». Второй прогон после изменения файла (новый sha256) — `-2`, старый
   файл цел.
3. Коллизии: два разных файла с одним именем → два файла с именами `…`, `…-2`; регистр — по
   правилу §6.1; недопустимые имена и имена устройств Windows заменяются; `{hash8}` убирает
   коллизию гарантированно.
4. Ни один существующий файл не перезаписан, не удалён и не переименован; `--out` не равен
   каталогу архива; симлинк-режим не разыменовывает цели.
5. GUI: «Выгрузить на диск…» открывает те же поля (каталог, режим, шаблон), сначала показывает
   план, кнопка «Выгрузить N файлов» появляется после плана; прогресс и «Стоп» — в верхней панели,
   как у индексации.
6. Тесты: матрица коллизий §6.1 (все четыре вида), идемпотентность, `-2` при другом содержимом,
   отсутствующий исходник, отказ `--out` внутри корня, dry-run ничего не создаёт, 0 байт для
   `hard`, отмена не оставляет недописанных файлов (созданные до отмены перечислены в отчёте).
7. Замер на корпусе: выгрузка альбома из 500 файлов `hard` (время, байт), повтор — время и 0
   новых; 2230 файлов `copy` — время и объём; числа в `docs/ARCHITECTURE.md` §Замеры.
8. ADR 0035 «Выгрузка: план, ссылки по умолчанию, ничего не перезаписывается».

### 6.4. Не делать в M20

- Не удалять и не «синхронизировать» `--out`: устаревшие файлы остаются, владелец решает сам.
- Не писать в `--out` служебные файлы (манифест, `.photocat/`, JSON) — каталог выгрузки остаётся
  чистым набором снимков.
- Не выгружать автоматически по расписанию, при старте или при изменении альбома.
- Не считать `--out` архивом и не индексировать его молча.

## 7. Порядок работ

1. M18 (мультивыбор) — иначе «Добавить выбранные» нечего нажимать.
2. M19: схема → `db` → CLI → тесты миграции на копии реальной БД → вид «Альбомы» → `docs`.
3. M20: `plan_album` + коллизии → CLI `--apply` → GUI-план → замеры → ADR 0035.

## 8. Открытые вопросы к владельцу

1. ~~Слово~~ Решено владельцем (2026-11-23): **«Альбомы»**; «альбом = день календаря» отменено.
2. **Режим выгрузки по умолчанию:** ссылки (0 байт, ломаются при переносе архива) или копии
   (безопасно, но место)? Предлагаю ссылки, как в витрине.
3. **Структура:** плоско в один каталог или подкаталоги по дням/месяцам? Предлагаю плоско —
   альбом уже смысловая группа.
4. **Коллизия без шаблона:** `-2` (читаемо) или `_a1b2c3` (стабильно и без «второй файл хуже
   первого»)? Предлагаю `-2`, `{hash8}` — по желанию.
5. **Умные альбомы** (правило «тег + дата», обновляется само) — это уже фильтр, а не альбом.
   Делать отдельно или не делать?
