# Проектировать интерфейс photocat

Владелец разбирает семейный архив: 2784 фото, 525 видео, 65 ГБ, всё в куче. Он не дизайнер и не
фотограф. Его задача — **найти, понять, разложить**. Интерфейс обязан быть плотным, тихим и
предсказуемым: сетка снимков, одна строка статуса, панель фильтров. Этот скилл — процедура и
рубрика, а не эссе о красоте.

## Источники правды

изменением.

## Процедура

1. **Бриф в пять строк** до кода: какой экран, чья задача, главное действие (одно!), плотность
   (панель/сетка/тултип), что убираем. Два главных действия на экране — бриф не написан.
2. **Два-три варианта** с ценой в коде и в привычке пользователя. Один вариант — не дизайн,
   три — спор. По строке компромисса на каждый.
3. **Выбор по рубрике** (ниже), а не по вкусу. «Выглядит чище» — не критерий.
4. **Запись** в `docs/UI.md` (метрика/экран/текст) и в `docs/DECISIONS.md`, если решение
   необратимо (новый вид, новая колонка, смена структуры витрины).
5. **Реализация через существующие виджеты.** Сетку рисует `draw_cell`; новый экран её вызывает.
   Второй экземпляр плитки — дефект.
6. **Проверка**: см. §Проверка.

## Рубрика (оценивать по пунктам, вслух)

1. **Одно главное действие.** На сетке — «Индексировать»; в дублях — «Найти группы». Остальное
   вторично и не спорит с ним по весу.
2. **Узнавание вместо поиска.** Плитка = картинка + дата. Никаких иконок-загадок и легенд.
3. **Число всегда с единицей и всегда рядом с подписью**: «зря 214.1 МиБ», а не «214.1».
4. **Состояние видно, а не угадывается.** Идёт индексация → прогресс `done/total`, статус-строка
   с путём. Нет превью → текст на плитке, а не серая пустота.
5. **Ничего не появляется только по наведению.** Тултип — подсказка, не единственный способ.
6. **Отклик моментален.** Клик выделяет в том же кадре; тяжёлое уходит в поток с прогрессом.
7. **Плотность.** 150 px ячейка, 260 px панель, 11 px подпись: на 1240×840 видно ≥ 40 снимков.
   Любое увеличение метрик — с обоснованием в `docs/UI.md`.
8. **Слова.** Инфинитив в кнопке, факт+число в статусе, без «Успешно!» и без «файл(ов)».
9. **Ничего не разрушается.** В интерфейсе нет слов «удалить», «переместить», «очистить».
   Максимум — «пометить лишним» и «экспорт плана».

## Человеческие факторы (числа, а не вкус)

- **Цель клика** ≥ 32 px; у нас 150 px с запасом — не уменьшать.
- **Время отклика:** до 100 мс — мгновенно; до 1 с — терпимо без индикатора; больше — обязателен
  прогресс. Декод картинки для превью в UI-потоке = больше 1 с → только из кэша.
- **Закон Хика:** в панели не больше 5–7 пунктов одного веса.
- **Закон Фиттса:** главная кнопка — у верхней границы, не в середине экрана.
- **Контраст:** текст на тёмной теме — не ниже `gray(190)`; подписи не светлее `gray(150)`.

## Проверка

Беззвучно по умолчанию — сессия не должна занимать экран владельца:

1. `cargo clippy --all-targets` — ошибок нет.
2. `bash .pi/skills/enforce-architecture/scripts/check.sh` — `egui` только в `app.rs`.
3. Логика экрана проверяется без GUI: `index` / `dupes` / `organize` на корпусе (см.
   `corpus-bench`). Если новый вид меняет только раскладку — достаточно компактной выборки.
4. Пиксели (цвета, контраст, тултип, тема) headless-проверкой не покрываются: нужен запуск
   `timeout 6 ./target/release/photocat gui` **с предупреждением владельцу** или его собственный
   просмотр.

UI-изменение не готово, когда компилируется. Оно готово, когда результат посмотрели.

## Когда остановиться и спросить владельца

- Новый экран или новый вид (число вкладок растёт).
- Новая метрика (ячейка, панель, размер превью) — это видно каждый день.
- Смена структуры витрины на диске.
- Удаление существующей возможности.
- Текст, который обещает то, чего код не делает (например, «удалить» при отсутствии удаления).
